# VALIDATION.md — как устроена локальная валидация и почему

> Спецификация для людей и агентов обоих участников. Цель: локальный AIC на `val-report`
> совпадает со скором лидерборда в пределах шума (±0.015). Каждое решение здесь принято
> через обсуждение и записано в [DECISIONS.md](DECISIONS.md) (D-01 … D-10). Менять что-либо
> из этого файла = новая версия валидации (см. §7), а не правка на месте.

## 1. Как организаторы считают AIC (точная логика, которую повторяет `src/metric.py`)

Для каждого тестового изображения читается наш PNG и GT-маска организаторов, обе в
**исходном разрешении картинки**. Дальше:

1. **Positive / negative определяет GT**, не мы: GT непустая → positive, пустая → negative.
2. **Positive:** `Dice_i = 2·|P∩G| / (|P| + |G| + 1e-6)` считается **на каждой картинке отдельно**,
   потом среднее по всем positive. Пустое предсказание на positive = 0. Маска в 0.1 % кадра весит
   столько же, сколько маска в 50 % кадра.
3. **Negative:** Dice не считается. Ложная тревога, если `|P| / (H·W) ≥ 0.01`. FPR_neg = доля
   негативов с ложной тревогой. Мусор < 1 % кадра бесплатен; 1 % и 90 % площади штрафуются одинаково.
4. `AIC = 2·Dice_pos·(1−FPR_neg) / (Dice_pos + (1−FPR_neg))`. Гармоническое среднее тянется к
   меньшему слагаемому: Dice 0.95 и FPR 0.01 → 0.969 (уровень топ-1); Dice 0.95 и FPR 0.30 → 0.81.

Следствия, которые важно не перепутать:

- **Доля негативов в тесте на ожидаемый AIC не влияет.** Dice усредняется внутри позитивов, FPR
  внутри негативов; соотношение классов в формулу не входит. От доли зависит только **шум**:
  при ~2.6 % негативов (как в train) это ~56 картинок теста, одна ложная тревога = +1.8 % FPR
  ≈ −0.009 AIC.
- **Правило «обнулять маску при площади < 1 %» FPR не улучшает вовсе** (такие кадры и так не ложная
  тревога), зато обнуляет Dice на 5.8 % позитивов с мелкими правками. Порог площади нужен, но выше
  1 %, и подбирается по AIC (см. §5).
- **Бинаризация GT.** Код метрики не опубликован. Бейзлайн организаторов читает GT как `m > 128`,
  мы используем это же. Проверено на 6 000 масках train: при `>128` ни одна маска не становится
  пустой; 42 % масок содержат серые значения на границе; Dice между GT при `>0` и `>128` в среднем
  0.994 (минимум 0.865). То есть выбор порога даёт полосу неопределённости ~0.5 % Dice_pos.
  `metric.py` печатает AIC для обоих порогов. Вопрос организаторам — отправить (§8).
- **Наши маски строго `{0, 255}`, режим `L`, размер = размеру картинки.** Несовпадение размера
  на платформе, скорее всего, ноль за весь сабмит. `metric.py` на этом **падает с ошибкой**.

## 3. Негативы: три пула (D-01)

| Пул | Откуда | Сколько доступно | Роль |
|---|---|---|---|
| `neg_train` | строки train с пустой GT (`_0003xxxx`) | ~2 700 | **основной**; ближе всего к тому, что организаторы называют negative |
| `neg_src` | `src`-оригиналы сцен, попавших в holdout | ~5k в val-tune, ~2.5k в val-report (берём до 2 000 / 1 000) | **основной**; hard negatives тех же доменов |
| `neg_nb` | `src`-оригиналы nanobanana | 2 000 случайных | **контрольный**: печатаем, при подборе порога не используем |

FPR печатается по каждому пулу отдельно. Для подбора порога используется
`FPR_main = (FPR_neg_train + FPR_neg_src) / 2` (равные веса, чтобы 2k src не «задавили» 1k настоящих).
Для сравнения с лидербордом основной репортуемый AIC считается с `FPR_main`; рядом печатаются
`AIC(neg_train)`, `AIC(neg_src)`, `AIC(neg_nb)`. Если пулы расходятся по FPR — это сигнал про модель,
разбираемся, а не перевешиваем.

`src`-оригиналы **train-сцен** в валидации не используются (модель видела сцену), но могут идти в
обучение как негативы — это уже решение про обучение, не про валидацию.

## 4. Разбиение (D-02, D-03, D-06)

- **Единица разбиения — сцена** (`group_id`), не строка. `group_id` вытаскивается из имени:
  coco → `coco_000000059319`; raise → `raise_rbda4cda5t`; openimages → `openimages_<hex>`;
  D-семейства → `D17_I_nat_0074` / `D44_L4S4C3`; 9-значные → сам id; негативы → сам id.
  Все правки одной сцены и её `src` идут в одну роль. `make_split.py` содержит тест на утечку.
- **20 фолдов по ~5 % сцен**, group-стратифицированно по домену и генератору (`StratifiedGroupKFold`,
  `seed=42`). Роли: `val-tune` = фолды {0, 1} (~10k), `val-report` = фолд {2} (~5k),
  `train` = фолды {3…19} (~88k). Резерв: 5-fold CV = 4 фолда на блок, split не пересобирается.
- **Негативы `neg_train` распределяются иначе**: 60 % сцен в holdout (в пропорции 2:1 между
  val-tune и val-report → ~1 080 / ~540), 40 % (~1 080) в train. Пропорциональный 10 % дал бы
  ~270 негативов для FPR — слишком шумно.
- **Домены и генераторы пропорционально train** (тест похож на train). Разрез по доменам печатается
  отдельной таблицей, общий AIC остаётся сравнимым с лидербордом.
- **`proxy`** = 1 500 позитивов из фолда 0 + все негативы val-tune; фиксированный список, по нему
  считается быстрый AIC внутри обучения (D-08).
- Битые пары (маска ≠ размер картинки) **выкидываются** и из holdout, и из обучения (список в
  `splits/stage1_v1_dropped.csv`).

## 5. Порог и постобработка (D-05)

Параметры, которые двигают AIC напрямую: порог вероятности `t` и минимальная площадь `a_min`
(если белого < `a_min` кадра — маска обнуляется целиком). Позже возможен третий: порог image-level
классификатора.

1. Вероятности модели на val-tune сохраняются один раз (`.npy`/`.png` 8-бит).
2. Сетка `t × a_min`, для каждой пары полный AIC на val-tune.
3. Выбирается **центр самого широкого плато** (диапазон, где AIC ≥ max − 0.002), а не точка максимума.
4. Пара замораживается, применяется к val-report и к тесту.
5. **На val-report ничего не подбирается.** Посмотрел val-report → поменял модель → это уже tune.
   val-report смотрим один раз перед сабмитом, число пишем в `experiments.md`.

## 6. Три уровня оценки (D-04, D-08)

| Уровень | Где | Что | Когда |
|---|---|---|---|
| `loss` | в цикле обучения | BCE/Dice loss на val-tune | каждая эпоха |
| `proxy` | в цикле обучения | Dice per image + FPR на тензорах в рабочем разрешении, `t=0.5`, без `a_min`, на подмножестве `proxy` | каждая эпоха, секунды |
| `full` | `src/metric.py` | PNG в исходном разрешении через формат сабмита, подбор `t × a_min` | лучший чекпоинт; опционально каждая эпоха (`--select-by full`, ~2–4 мин) |

Флаг `--select-by {loss,proxy,full}`, по умолчанию `proxy`. На первых обучениях считаем все три и
проверяем, одинаково ли они ранжируют чекпоинты; если proxy согласен с full, живём на proxy.

`metric.py` принимает `submission.csv` + `predictions/` + csv с GT, печатает: AIC, Dice_pos,
FPR по пулам, AIC при GT `>0` и `>128`, долю пустых предсказаний на позитивах, Dice по корзинам
площади (< 1 %, 1–5 %, 5–20 %, > 20 %), таблицу по доменам и генераторам, `VERSION` валидации.
Падает, если хоть один PNG не `L`/не `{0,255}`/не того размера или не хватает строки в csv.

## 8. Калибровка по лидерборду (D-07)

1. Первый сабмит — бейзлайн организаторов, обученный **нашим** пайплайном на **нашем** split
   (UNet-R34, 256², наш порог). Даёт первую пару (val-report, LB) и отвечает на вопрос
   «скор бейзлайна = порог для 1 балла».
2. Вторая калибровочная точка — та же модель с другим порогом **из того же плато** (край плато).
   Оба сабмита заранее помечены в `experiments.md` как калибровочные. Итоговый порог всё равно
   выбирается только по val-tune, лидерборд на него не влияет.
3. **Полоса шума ±0.015** (≈ одна ложная тревога на ~56 негативах теста + полоса бинаризации GT).
   Расхождение больше → стоп, чиним валидацию/формат, тщательно думаем, только потом новые сабмиты.
   Второе условие: два порога должны двигать LB в ту же сторону, что и val-report; иначе тоже стоп.
4. Сабмит уходит только с парой (чекпоинт, порог), которая **уже записана** в `experiments.md`
   с val-tune и val-report числами.
5. Учитывать лимит сабмитов на платформе (уточнить): калибровка съедает два.

Вопросы организаторам (support@aiijc.com), связанные с валидацией: порог бинаризации GT (`>0` или
`>128`); есть ли лимит сабмитов; из чего состоят negative-примеры теста.

## 9. Правила про тест (напоминание)

Тест только для финального инференса. Запрещено: pseudo-labeling, адаптация BN, подбор порога
по распределению предсказаний на тесте, перебор порогов сабмитами. Единственная допустимая
«статистика» — уже сделанное наблюдение, что размеры/JPEG теста совпадают с train, и оно ни на
какое решение не влияет. Дальше тест для аналитики не открываем.
